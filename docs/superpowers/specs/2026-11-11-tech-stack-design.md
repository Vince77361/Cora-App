# Cora 기술 스택 설계

- 작성일: 2026-11-11
- 상태: 소유자 검토 대기
- 범위: 기술 스택과 레포 구조, 외부 연동 방식. 기능별 상세 설계와 DB 스키마는 이 문서의 범위가 아니다.

표기: **[결정]** 소유자가 직접 정함 · **[합의]** 제안을 소유자가 승인함 · **[제안]** 작성자의 판단이며 소유자 확인 전

## 1. 무엇을 만드는가

Cora는 가게 사장님·브랜드와 크리에이터를 이어 주는 한국 대상 모바일 앱이다. 스와이프로 서로를 발견하고, 대화로 조건을 맞추고, 계약하고, 에스크로로 결제하고, 콘텐츠 조회수에 따라 지급한다.

- 기획 원본: https://claude.ai/artifact/VLvHYafMkwqziRViALPicw (38종 화면, 라이트·다크 각각)
- 코드 레포: https://github.com/Vince77361/Cora-App (현재 비어 있음)
- 코딩 패턴 기준: https://github.com/Vince77361/Vince_Wiki

### 역할 세 가지

| 역할 | 첫 화면 | 화면 묶음 |
|---|---|---|
| 가게 사장님 (소상공인 1차 MVP) | 가게 링크 입력 | A2~A5, A8, A9, B1, B4, B7 |
| 브랜드 | 크리에이터 발견(스와이프) | 01~07, 10~15, D3~D5 |
| 크리에이터 | 협업 원칙 정하기 | 08, 09, A6, A7, B2, B3, B5, B6, D1, D2 |

유입 전략 화면(C1 외부 리스트 검색, C2 미가입 계정에 연락)은 기획에서 "검토 중"이다.

## 2. 목표와 제약

### 목표

- **[결정]** 한국 출시. iOS와 Android 모두.
- **[결정]** 기획의 모든 화면이 첫 출시 범위다. "논의 중"·"검토 중" 화면도 포함한다.
- **[결정]** 시각 완성도와 페이지 전환 애니메이션이 가장 중요한 품질 기준이다.

| 2027년 1월 중순 | 개발 완료 |
| 2027년 1월 말 | 테스트 시작 |
| 2027년 2월 | 배포 (목표일이며, 외부 승인이 늦으면 미룬다) |

- **[결정]** 1인 개발. Flutter와 React Native 모두 경험이 있다.
- **[결정]** 사업자 등록은 완료. PG 계약과 Meta 앱 심사는 아직 시작하지 않았고 최대한 뒤로 미룬다.
- **[결정]** 화면과 백엔드를 먼저 만들고, 외부 연동은 나중에 붙인다.

- 외부 연동을 붙일 때 화면이나 서버 로직을 다시 써야 하는 것
- 가짜 구현이 실서비스에서 동작하는 것

## 3. 스택

| 영역 | 선택 | 근거 |
|---|---|---|
| 앱 | Flutter + Riverpod | **[합의]** |
| 앱 라우팅 | go_router, 커스텀 페이지 전환과 공유 요소 전환 | **[합의]** |
| 백엔드 | NestJS + Prisma | **[결정]** |
| DB | Supabase PostgreSQL (Pro 플랜) | **[결정]** |
| 로그인 | Supabase Auth | **[결정]** |
| 파일·영상 저장 | Supabase Storage | **[결정]** |
| 실시간 대화 | NestJS WebSocket 게이트웨이 | **[합의]** |
| 예약 작업 | NestJS 스케줄러 + 작업 큐(Redis) | **[합의]** |
| API 계약 | Swagger(OpenAPI) → Dart 클라이언트 자동 생성 | **[합의]** |
| 백엔드 패키지 매니저 | yarn | **[합의]** |
| 서버 호스팅 | 미정 | 5.3 참고 |

### 선택 이유

**Flutter (Expo 대신).** 화면을 직접 그리므로 두 플랫폼의 결과가 같다. 기획 전반의 반투명 블러 카드와 넓은 그림자는 React Native의 Android에서 품질이 떨어진다. 1인 개발에서 플랫폼별 시각 차이를 잡는 시간을 줄이는 것이 언어 통일보다 중요하다고 판단했다. 포기한 것은 백엔드와의 타입 공유와 심사 없는 즉시 배포다. 타입 공유는 Dart 클라이언트 자동 생성으로 메운다.

**NestJS (Go Fiber 대신).** Swagger가 데코레이터에서 자동으로 나오고, JSON이 camelCase라 Dart와 그대로 맞고, WebSocket·스케줄러·작업 큐가 공식 모듈로 있다. Wiki에 NestJS 규칙이 확정돼 있는 반면 Go의 데이터 접근 계층 기준은 미정이다. Go의 성능 이점은 초기 규모에서 쓰이지 않는다.

**Supabase를 DB·로그인·저장소까지.** 카카오와 Apple 로그인을 기본 지원하고 저장소 설정이 필요 없어 1인 개발량이 준다. 대화와 데이터 읽기·쓰기는 Supabase에 맡기지 않는다. 돈과 계약 로직을 NestJS 한곳에 모으기 위해서다.

## 4. 구조

### 4.1 레포

**[합의]** Cora-App 하나에 앱과 서버를 함께 둔다.

```text
Cora-App/
├── app/            # Flutter
├── api/            # NestJS (yarn)
├── supabase/       # Supabase CLI 설정 (로컬 개발용)
├── docs/superpowers/
│   ├── specs/      # 설계 문서
│   └── plans/      # 실행 계획
└── docker-compose.yml   # Redis
```

git 규칙은 Wiki의 [Git and commit workflow]를 따른다: 한국어 conventional commit, 원자적 커밋, feature 브랜치.

### 4.2 데이터 흐름

```text
Flutter 앱 ──(REST, WebSocket)──→ NestJS ──(Prisma)──→ Supabase PostgreSQL
    │                               │
    ├──(로그인)──→ Supabase Auth    ├──(토큰 검증)──→ Supabase Auth
    └──(파일 업로드)──→ Supabase Storage ←──(서명 URL 발급)──┘
```

- **[합의]** 앱은 데이터를 NestJS API로만 읽고 쓴다. Supabase의 자동 생성 데이터 API는 쓰지 않는다.
- **[합의]** 앱이 Supabase에 직접 닿는 곳은 로그인과 파일 업로드 두 곳뿐이다.
- **[제안]** 파일 업로드는 NestJS가 서명된 업로드 URL을 발급하고 앱이 그 주소로 직접 올린다. 영상이 API 서버를 거치지 않게 한다.
- **[제안]** NestJS는 Supabase Auth가 발급한 JWT를 검증해 사용자를 식별한다. 역할(가게·브랜드·크리에이터)과 프로필은 NestJS가 관리하는 테이블에 둔다.

### 4.3 Supabase 사용 규칙

- **[합의]** 모든 테이블에 RLS를 켜고 정책은 비워 둔다. 자동 생성 API로 DB를 직접 읽는 길을 막기 위해서다. Prisma는 RLS를 우회하는 서버 전용 연결을 쓴다.
- **[합의]** 연결 주소는 두 개다. 서버 실행에는 풀링 주소, Prisma 마이그레이션에는 직접 연결 주소.
- **[합의]** 스키마와 마이그레이션은 Prisma가 관리한다. Supabase 대시보드에서 테이블을 직접 고치지 않는다.
- **[제안]** 서비스 역할 키는 NestJS 환경변수에만 둔다. 앱에는 공개 키만 넣는다.
- **[제안]** Supabase 프로젝트는 개발용과 운영용 두 개로 나눈다. 로컬 개발은 Supabase CLI로 띄운다.

### 4.4 앱 (Flutter)

Wiki의 [App Clean Architecture with MVVM]과 [Flutter and Riverpod]를 따른다.

- `lib/features/<feature>/{data,domain,presentation/{pages,viewmodels}}` + `lib/core/`
- 의존 방향: `presentation → domain ← data`
- ViewModel은 Riverpod `AsyncNotifier`, 이름 `*ViewModel`
- 저장소는 `domain`의 추상 포트를 `data`가 구현. provider는 기본값을 `UnimplementedError`로 두고 `main.dart`에서 실제 구현으로 override
- 엔티티는 손으로 쓴 불변 클래스 (freezed 미사용)
- **[제안]** 예외: API 통신 계층은 OpenAPI에서 생성한 Dart 클라이언트를 쓴다. 생성된 타입은 `data` 안에만 머물고 `domain` 엔티티로 변환한다.
- **[제안]** usecase 계층의 적용 깊이는 미정이다(5.2 참고).
- **[제안]** 기획의 색·글꼴·둥근 모서리·그림자 값은 `core/theme`에 토큰으로 모은다. 라이트·다크는 같은 화면 코드에 테마만 바꿔 적용한다.

### 4.5 백엔드 (NestJS)

Wiki의 [NestJS rules]를 따른다.

- 기능별 모듈, controller → service → repository 3계층. 백엔드는 간편형을 허용하지 않는다.
- 다른 모듈의 내부 파일을 import하지 않고 `exports`한 provider만 주입한다.
- Prisma 호출은 repository에만 둔다. 스키마 필드는 camelCase, 컬럼과 테이블은 `@map`·`@@map`으로 snake_case.
- class-validator + class-transformer. 입력 DTO와 출력 모델을 분리한다.
- JSON 키는 camelCase. 오류 응답은 `{ error: { code, message, details } }`.
- 그 밖에 Wiki의 Security baseline, Input validation, API contract, Error handling, Security logging, Database lifecycle and soft delete, Testing strategy를 적용한다.

### 4.6 외부 연동: 포트와 가짜 구현

**[합의]** 외부 연동은 전부 인터페이스(포트) 뒤에 둔다. 처음에는 가짜 구현으로 채우고 나중에 실제 구현으로 교체한다. 포트는 NestJS 쪽에 둔다. 앱은 연동이 가짜인지 진짜인지 알지 못한다.

| 연동 | 처음 (가짜) | 나중 (실제) |
|---|---|---|
| 결제·에스크로 | 항상 성공하는 결제 | PG사 |
| 인스타그램 (게시물 가져오기, 조회수) | 고정 샘플 게시물과 조회수 | Meta API |
| AI 콘텐츠 초안 | 고정 샘플 문안 | LLM API |
| 가게 링크 → 페이지 자동 생성 | 샘플 가게 정보 | 실제 링크 분석 |
| 푸시 알림 | 로그 출력 | FCM, APNs |
| 소셜 로그인 | Supabase Auth 이메일 로그인 | Supabase Auth 카카오, Apple |

규칙:

- **[합의]** 에스크로 장부, 계약 상태, 정산 계산은 처음부터 실제로 구현하고 DB에 기록한다. 가짜인 것은 PG사와 주고받는 부분뿐이다.
- **[제안]** 가짜 구현은 이름에 `Fake`를 붙이고 환경설정으로 선택한다. 운영 환경에서 가짜 구현이 선택되면 서버가 시작을 거부한다. Wiki의 "목으로 동작하는 척하지 않는다" 원칙과 충돌하지 않도록 하기 위한 장치다.
- **[제안]** 포트의 모양은 실제 서비스의 제약을 반영해 정한다. 예: 결제는 승인·취소·웹훅 수신이 분리된 비동기 흐름으로 설계한다.

## 5. 열린 문제와 위험

### 5.1 외부 승인 대기 시간

소유자는 연동을 뒤로 미루기로 했다. 다만 아래는 신청 후 대기가 있어 구현과 별개로 신청 시점을 잡아야 한다. 2월 배포에 맞추려면 12월 중순 전 신청을 권한다. 소유자는 2월을 목표일로만 보며, 승인이 늦으면 출시를 미루기로 했다.

- **PG 계약 심사**: 통과해야 실결제가 열린다.
- **에스크로 구조**: Cora가 대금을 직접 보관했다가 지급하는 구조는 전자금융 관련 등록 대상일 수 있다. PG사의 정산 대행으로 풀 수 있는지 확인이 필요하다. 법률 확인 사안이며 이 문서는 결론을 내리지 않는다.
- **Meta 앱 심사**: 게시물 가져오기와 조회수 집계에 필요하다.
- **미가입 계정 연락(C2)**: 인스타그램 정책에 따라 구현 방식이 제한될 수 있다.
- **스토어 심사**: Apple·Google 개발자 계정과 심사 기간.

### 5.2 일정 대비 범위

1인이 약 9주에 38종 화면 전체를 만드는 것은 빠듯하다. 범위는 줄이지 않기로 했으므로 순서로 위험을 줄인다.

- **[제안]** 개발 순서: 공통 기반(테마, 로그인, 역할 선택) → 가게 사장님 흐름과 결제 → 브랜드 탐색·협업 → 크리에이터 → "논의 중"(B1~B7) → "검토 중"(C1~C2).
- **[제안]** usecase 계층은 비즈니스 규칙이 있는 기능(오퍼, 계약, 에스크로, 입찰)에만 두고, 단순 조회 화면은 ViewModel이 저장소를 직접 호출한다. Wiki 기준으로 이 앱은 전체 형태 대상이므로 소유자 확인이 필요하다.

### 5.3 아직 정하지 않은 것

- NestJS 서버 호스팅 (WebSocket과 상시 실행 작업 큐를 지원해야 함)
- Redis 호스팅
- CI 구성, 앱 배포 자동화
- 영상 처리(썸네일, 변환)를 어디서 할지. Supabase Pro의 파일 크기 제한과 전송량 요금을 릴스 화면 설계 전에 확인해야 한다.
- 오류 추적과 분석 도구

### 5.4 검토 질문에 대한 소유자 답변

- **[결정]** 2월 배포는 목표일 뿐이다. 외부 승인이 늦어지면 출시를 미룬다. 따라서 기능별로 켜고 끄는 장치는 만들지 않고, 모든 연동이 실제 구현으로 교체된 뒤에 출시한다.
- **[결정]** 이메일 로그인은 개발 전용이다. 정식 로그인은 카카오와 Apple뿐이며, 가입·이메일 인증·비밀번호 재설정 화면은 만들지 않는다.
- **[제안]** 이메일 로그인은 두 곳에서 막는다. 운영용 Supabase 프로젝트에서 이메일 로그인을 끄고, 앱의 운영 빌드에서는 이메일 로그인 화면을 빼고 빌드한다.

## 6. 검토 후 추가한 판단

검토자의 질문 가운데 작성자가 정한 것이다. 모두 **[제안]**이다.

- **"개발 완료"의 뜻.** 1월 중순의 개발 완료는 가짜 구현 기준으로 모든 화면과 서버 로직이 동작하는 상태다. 실제 연동 교체는 승인이 나는 순서대로 그 뒤에 한다.
- **기획 원본의 성격.** 원본은 색·글꼴·간격·그림자 값이 들어 있는 클릭 가능한 HTML 목업이다. 이 값들을 확정값으로 보고 그대로 토큰으로 옮긴다. 화면 사이의 전환 모션은 원본에 정의돼 있지 않다.
- **전환 모션.** 공통 전환 규칙(기본 페이지 전환, 카드 → 상세 공유 요소 전환, 바닥 시트, 스와이프 카드)을 공통 기반 단계에서 먼저 정하고 소유자가 실제 기기에서 승인한다. 화면별 모션은 그 규칙을 적용한다.
- **앱 화면이 필요한 연동.** 결제창을 띄우고 돌아오는 단계와 인스타그램 계정 연결 단계는 가짜 구현 단계에서도 화면 흐름에 넣는다. 가짜 구현은 그 단계에서 가짜 결제창과 가짜 연결 화면을 보여 준다. "앱은 가짜인지 모른다"는 원칙은 이 두 단계를 포함한 흐름 전체에 적용한다.
- **지급은 별도 포트.** 가게에서 돈을 받는 결제 포트와 크리에이터에게 돈을 내보내는 지급 포트를 나눈다. PG사 후보는 미정이며, 포트는 승인·취소·웹훅이 분리된 일반적인 비동기 흐름으로 설계한다.
- **문서 우선순위.** 이 문서와 Wiki가 어긋나면 이 문서가 우선한다. 소유자가 이 문서를 승인하면 **[제안]** 항목도 승인된 것으로 본다.
- **지원 기기.** 휴대폰만 지원한다(태블릿 전용 레이아웃 없음). 최소 버전은 iOS 16, Android 8(API 26)로 잡는다. 블러와 그림자의 성능은 중저가 Android 실기기 한 대에서 확인한다.
