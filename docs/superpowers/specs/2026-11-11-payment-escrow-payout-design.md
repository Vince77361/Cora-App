## 1. 무엇을, 왜

수락된 오퍼를 사장님이 결제하면 Cora가 금액을 보관하고, 크리에이터가 콘텐츠 링크를 제출한 뒤 7일간의 조회수에 따라 지급하고, 남은 금액을 사장님에게 돌려준다.

- **[회의]** "오케이 하면 결제를 하고, 시스템이 돈을 홀드하고 있다가, 만들어지면 돈이 주어진다." 보상의 기본은 성과(조회수) 기준이다.
- **[결정]** PG사와 주고받는 부분만 가짜 구현이다. 장부, 상태, 정산 계산은 처음부터 실제로 만든다.

### 하지 않는 것

- 실제 PG 결제와 실제 송금 (9번 계획)
- 브랜드의 고정 제작비 결제 화면 (5번 설계에서 이 설계의 결제 모듈을 재사용한다)
- 세금계산서, 현금영수증, 원천징수 처리 (7장의 확인 항목)
- 분쟁 조정 화면. 이번에는 "문의하기"로 운영자에게 연결만 한다.

### 실패로 보는 것

- 장부의 합이 맞지 않는 것. 들어온 돈 = 지급한 돈 + 돌려준 돈 + 수수료 + 아직 보관 중인 돈이 항상 성립해야 한다.
- 같은 결제나 지급이 두 번 처리되는 것
- 조회수 집계가 멈춰 지급이 무기한 미뤄지는 것

## 2. 협업이라는 단위

**[제안]** 오퍼가 수락된 뒤의 일을 담는 `협업(collaboration)`을 만든다. 이후의 대화(5번), 제작과 검토(6번)도 이 단위에 붙는다. 가게 오퍼에서 온 협업과 브랜드 매칭에서 온 협업(4·5번)이 같은 테이블을 쓴다.

가게 오퍼에서 온 협업의 진행:

```text
오퍼 수락 ──→ AWAITING_PAYMENT ──(결제)──→ FUNDED ──(링크 제출)──→ COUNTING ──(7일)──→ SETTLED
                     │                        │
                     └─(3일 경과·취소)→ 종료   └─(제출 기한 경과)→ REFUNDED
```

- `AWAITING_PAYMENT`: 2번 설계의 "수락함, 결제를 기다려요"와 같다. 협업 행은 수락 시점에 만든다.
- `FUNDED`: 결제가 끝나 금액을 보관 중이다. 크리에이터가 방문하고 촬영한다.
- `COUNTING`: 링크가 제출되어 7일간 조회수를 센다.
- `SETTLED`: 지급과 환급이 끝났다.
- `REFUNDED`: 링크가 제출되지 않아 전액을 돌려줬다.
- **[제안]** 보상이 식사권뿐인 오퍼는 결제할 금액이 없다. 수락하면 바로 `FUNDED`가 되고, 링크가 제출되면 집계 없이 `SETTLED`가 된다.

## 3. 화면별 동작

### A8 가게 결제 (사장님)

- **[화면]** 제목 "{활동 이름}이 오퍼를 수락했어요". 내역: 콘텐츠 "릴스 1편", "2인 식사권 · 방문 때 가게에서 제공", "조회수당 (최대) 100,000원", "서비스 수수료 [수수료]", "지금 결제할 금액 100,000원+".
- **[화면]** "조회수가 적어 다 쓰지 않은 금액은 7일 집계 후 돌려드려요."
- **[화면]** 결제 수단: 카드, 계좌이체, 간편결제. 버튼 "결제하고 보관 맡기기".
- **[제안]** 결제할 금액 = 조회수당 상한 + 서비스 수수료. 수수료는 상한의 10%로 가정하고 설정값으로 둔다(7장).
- **[제안]** 버튼을 누르면 결제창이 뜬다. 이번에는 가짜 결제창이다: 금액과 "결제 승인", "결제 실패" 버튼이 있는 화면. 승인하면 사장님 홈으로 돌아가고 "결제했어요. 크리에이터에게 알렸어요."를 보여 준다.
- **[제안]** 결제가 실패하거나 창을 닫으면 A8로 돌아오고 "결제가 완료되지 않았어요. 다시 시도해 주세요."를 보여 준다.
- **[제안]** 결제 완료 여부는 결제창의 결과가 아니라 서버가 PG에서 받은 통지로 판단한다. 앱은 돌아온 뒤 서버에 상태를 묻는다.

### A7 에스크로 결제·지급 (크리에이터)

- **[화면]** 머리 "{가게 이름} 협업". 상자: "Cora가 안전하게 보관 중", "100,000원", "+ 2인 식사권 (방문 때 사용)", "지금 받을 금액 43,200원", "조회수 4,320회".
- **[화면]** 단계: 오퍼 수락 → 가게 결제 완료 → 방문하고 촬영하기 → 콘텐츠 올리고 링크 제출 → 7일간 조회수 집계 후 지급.
- **[화면]** 버튼 "문의하기", "콘텐츠 링크 제출".
- **[제안]** "지금 받을 금액"과 "조회수"는 링크 제출 뒤에만 숫자가 나온다. 그 전에는 "링크를 제출하면 집계가 시작돼요."
- **[제안]** 링크 제출 화면: 주소 입력란 하나와 "제출하기". 형식에 맞는 주소만 받는다(쇼츠는 유튜브, 릴스와 카드뉴스는 인스타그램, 블로그 글은 네이버 블로그·티스토리). 제출 뒤에는 고칠 수 없고, 잘못 넣었으면 "문의하기"로 연락한다.
- **[제안]** 식사권은 이 화면에서 "식사권 보여주기"를 누르면 가게 이름, 식사권 이름, 협업 번호가 큰 글자로 보인다. 사용 확인 절차는 만들지 않는다.
- **[제안]** "문의하기"는 운영자 이메일로 가는 메일 작성 화면을 연다. 제목에 협업 번호가 들어간다.

### 사장님 쪽 진행 화면 (캔버스에 없음)

- **[제안]** 사장님 홈의 "진행 중" 줄을 누르면 A7과 같은 구성의 화면이 열린다. 차이: "보관 중인 금액", "현재 조회수", "예상 환급액", 제출된 콘텐츠 링크(누르면 열림).

## 4. 규칙

### 기한

| 기한 | 값 | 지나면 |
|---|---|---|
| 수락 후 결제 | 3일 (2번 설계) | 오퍼 만료, 협업 종료 |
| 결제 후 링크 제출 | 14일 | 전액 환급(수수료 포함), `REFUNDED` |
| 조회수 집계 | 제출 후 7일 | 정산 |

- **[제안]** 제출 기한 3일 전과 하루 전에 크리에이터에게 알림을 보낸다.

### 조회수와 정산

- 조회수는 `ViewCountPort`로 읽는다. 제출 직후 한 번(기준값), 그 뒤 하루에 한 번, 7일째에 마지막으로 읽는다.
- 브랜드 계약의 고정 제작비 정산, 결제 뒤 취소, 운영 명령, 인스타그램 연동 조건은 공통 규칙 2장에 있다.
- **[제안]** 지급 대상 조회수 = 7일째 조회수. (기준값을 빼지 않는다. 제출 직후의 조회수는 대개 0에 가깝다.)
- 정산은 7일째에 확정하고, 송금은 그 주의 다음 주 수요일 10시에 모아서 한다(공통 규칙 2장(2026-11-11 소유자 결정)).
- 지급액 = `min(조회수 × 단가, 상한)`. 환급액 = `상한 − 지급액`. 수수료는 돌려주지 않는다.
- **[제안]** 조회수를 3일 연속 읽지 못하면 운영자에게 알리고 그 협업의 정산을 멈춘다. 자동으로 0원 정산하지 않는다.
- **[제안]** 링크가 삭제되거나 비공개가 되어 읽을 수 없으면 마지막으로 읽은 값으로 정산한다.

### 장부

- 모든 돈의 움직임은 장부에 두 줄(나가는 쪽, 들어오는 쪽)로 적는다. 금액은 원 단위 정수다. 한 번 적은 줄은 고치지 않고, 정정은 반대 줄을 더한다.
- 계정: `PG_수납`, `보관`, `크리에이터_지급`, `가게_환급`, `수수료_수익`.
- 결제 승인 시: `PG_수납` → `보관`(상한), `PG_수납` → `수수료_수익`(수수료).
- 정산 시: `보관` → `크리에이터_지급`(지급액), `보관` → `가게_환급`(환급액).
- 전액 환급 시: `보관` → `가게_환급`(상한), `수수료_수익` → `가게_환급`(수수료).
- 결제 통지, 정산, 지급, 환급에는 중복 방지 키를 쓴다. 같은 키로 두 번 들어오면 두 번째는 아무 일도 하지 않는다.

### 지급받을 계좌

- **[제안]** 크리에이터는 첫 지급 전에 은행, 계좌번호, 예금주를 등록한다. 등록 전에는 A7에 "지급받을 계좌를 등록해 주세요."가 보이고, 정산된 금액은 등록될 때까지 `크리에이터_지급`에 남는다.
- 계좌번호는 암호화해 저장하고, 로그에는 뒤 4자리만 남긴다. 화면에는 E4·E7 캔버스대로 뒤 2자리(`****12`)만 보인다(2026-11-11 소유자 결정).
- **[제안]** 이번에는 예금주 확인을 하지 않는다(가짜 지급). 실제 연동 때 PG의 계좌 실명 조회를 붙인다.

### 알림

| 사건 | 받는 사람 | 문구 |
|---|---|---|
| 결제 완료 | 크리에이터 | "{가게 이름}이 결제했어요. 방문하고 촬영해 주세요." |
| 링크 제출 | 사장님 | "{활동 이름}님이 콘텐츠를 올렸어요." |

## 5. 데이터와 서버 (윤곽)

| 테이블 | 담는 것 |
|---|---|
| `collaborations` | 종류(가게 오퍼·브랜드 계약), 맡기는 쪽, 크리에이터, 연결된 오퍼, 상태, 조건 사본, 제출 기한, 제출된 링크, 제출 시각 |
| `payments` | 협업, 금액(상한, 수수료), 수단, 상태(대기·승인·실패·취소), PG 거래 번호 |
| `ledger_entries` | 협업, 묶음 번호, 나가는 계정, 들어오는 계정, 금액, 사유, 중복 방지 키 |
| `view_snapshots` | 협업, 읽은 시각, 조회수 |
| `settlements` | 협업, 최종 조회수, 지급액, 환급액, 확정 시각 |
| `payouts` / `refunds` | 대상, 금액, 상태(대기·완료·실패), 외부 거래 번호 |
| `payout_accounts` | 크리에이터, 은행, 계좌번호(암호화), 예금주 |

### 새 연동 포트

- `PaymentPort`: 결제 요청 만들기(결제창 주소 또는 토큰 반환), 통지 검증, 취소·환불. 통지는 서버의 웹훅 주소로 들어온다. 가짜 구현은 앱의 가짜 결제창이 부르는 개발 전용 주소로 통지를 흉내 낸다.
- `PayoutPort`: 계좌로 송금 요청, 결과 조회. 가짜 구현은 항상 성공한다.
- `ViewCountPort`: 링크의 조회수 읽기, 링크가 그 크리에이터의 것인지 확인. 가짜 구현은 제출 후 지난 시간에 비례해 늘어나는 숫자를 돌려준다(하루 약 600회).
- 환경변수 `PAYMENT_ADAPTER`, `PAYOUT_ADAPTER`, `VIEW_COUNT_ADAPTER`.

### 작업 큐

이 계획에서 처음 도입한다(NestJS 작업 큐 + Redis).

| 작업 | 시점 |
|---|---|
| 조회수 읽기 | 제출 직후, 그 뒤 매일 |
| 정산 | 제출 후 7일 |
| 미제출 환급 | 결제 후 14일 |
| 제출 기한 알림 | 기한 3일 전, 1일 전 |
| 거절 알림 | 거절 후 30초 (2번 설계에서 미룬 것) |
| 결제 기한 만료 | 수락 후 3일 (2번의 조회 시 계산을 보완) |

작업은 여러 번 실행돼도 결과가 같아야 한다.

### 권한

- 결제는 그 협업의 사장님만, 링크 제출은 그 협업의 크리에이터만 한다.
- 장부와 정산은 당사자가 자기 협업의 요약만 읽는다. 장부 줄 자체는 앱에 내보내지 않는다.
- 웹훅 주소는 로그인 없이 열려 있으므로 `PaymentPort`의 서명 검증을 통과한 요청만 처리한다.

## 6. 법적 확인이 필요한 것

이 문서는 결론을 내리지 않는다. 실제 결제를 붙이기 전에 전문가 확인이 필요하다.

- **대금 보관.** Cora가 결제 대금을 보관했다가 제3자에게 지급하는 구조는 전자금융 관련 등록 대상일 수 있다. PG사의 정산·지급 대행 서비스를 쓰면 Cora가 돈을 직접 보관하지 않는 구조로 바꿀 수 있는지 확인한다. 이 경우에도 이 설계의 장부는 "누가 얼마를 받을지"의 기록으로 그대로 쓴다.
- **크리에이터 지급의 세금.** 개인에게 지급하는 대가의 원천징수와 신고 의무.
- **수수료의 증빙.** 사장님에게 발행할 영수증이나 세금계산서.
- **광고 표시.** 대가를 받은 콘텐츠의 광고 표시 의무를 앱이 어디까지 안내하고 확인할지.

## 7. 소유자 확인이 필요한 것

답이 없으면 **[제안]**대로 진행한다.

1. **서비스 수수료.** 캔버스에 "[수수료]"로 비어 있다. 상한의 10%, 사장님 부담으로 가정했다.
2. **식사권만 있는 오퍼.** 결제도 수수료도 없이 진행하게 했다. 이 경우에도 수수료를 받을지.
3. **제출 기한 14일.** 캔버스의 예시(11월 10일 수락, 11월 23일까지)에서 역산했다.
4. **미제출 시 전액 환급.** 수수료까지 돌려주게 했다.
5. **식사권 사용 확인.** 확인 절차를 만들지 않았다. 사장님이 "방문했어요"를 누르게 할지.
6. **조회수 기준.** 7일째의 조회수 전체를 지급 대상으로 봤다. 조회수의 정의(인스타그램의 재생 수인지 등)는 실제 연동에서 읽을 수 있는 값에 맞춘다.

- 계좌번호 암호화 방식(키는 환경변수로 받는다)
