## 1. 무엇을, 왜

1~8번에서 가짜 구현으로 만든 외부 연동을 실제 구현으로 바꾸고, 서버를 운영 환경에 올리고, 두 스토어에 앱을 낸다.

- **[결정]** 2월 배포는 목표일 뿐이다. 외부 승인이 늦으면 출시를 미룬다. 모든 연동이 실제 구현으로 바뀐 뒤에 출시한다.
- **[결정]** 운영 환경에서 가짜 구현이 하나라도 선택돼 있으면 서버가 시작을 거부한다.

이 문서는 연동마다 "무엇을 바꾸는지, 미리 무엇을 신청해야 하는지, 무엇이 아직 결정되지 않았는지"를 정리한다. 서비스별 세부 사양은 신청과 계약 뒤에 그 서비스의 공식 문서를 보고 각 실행 계획에서 정한다. 작성자가 기억으로 적은 사양은 틀릴 수 있으므로 이 문서에는 넣지 않았다.

## 3. 연동별 설계

### 3.1 로그인

- (2026-11-11 소유자 결정) Supabase 대시보드에서 휴대폰 로그인(SMS 업체 연결)과 카카오 제공자를 켜고, 운영 프로젝트의 이메일 로그인을 끈다. 네이버는 Supabase 기본 제공이 아니므로 별도로 연동한다.
- 앱의 로그인 화면(E1): 버튼 셋 — "휴대폰 번호로 시작하기"(E2 휴대폰 인증으로 이동), "카카오로 계속하기", "네이버로 계속하기". 공통 기반의 `AuthRepository`에 휴대폰 인증번호 요청·확인과 카카오·네이버 로그인이 있고, 개발 중에는 `SignInAdapter`의 가짜 구현이 같은 화면 뒤에서 개발용 계정으로 로그인시킨다. 서버는 바뀌지 않는다(Supabase가 발급한 토큰을 그대로 검증한다).
- **[확인 필요]** Apple 로그인은 출시 전에 다시 판단한다(2026-11-11 소유자 결정). 카카오·네이버 같은 소셜 로그인을 넣고 Apple 로그인을 빼면 App Store 심사 지침 4.8에 걸릴 수 있다(휴대폰 번호 로그인이 동등한 대안으로 인정되는지 확인). 위험으로만 기록한다.
- **[확인 필요]** Apple의 심사 지침은 계정을 만들 수 있는 앱에 앱 안에서의 계정 삭제를 요구한다. "회원 탈퇴"를 프로필 탭에 만든다(4장).

### 3.2 푸시 알림

- 앱이 기기 토큰을 서버에 등록한다. 테이블 `device_tokens`(사용자, 토큰, 플랫폼, 마지막 사용)를 더한다.
- 알림을 누르면 해당 화면으로 간다: 지원 → 사장님 홈, 오퍼 → 받은 오퍼, 메시지 → 대화방, 정산 → 협업 화면.
- 알림 권한은 첫 실행 때 묻지 않고, 처음으로 알림이 의미 있는 순간(가게 공개 직후, 첫 지원 직후)에 묻는다.
- **[제안]** 알림 종류별 켜고 끄기 화면은 만들지 않는다. 대화방별 끄기(5번 설계)와 기기 설정으로 충분하다고 본다.

### 3.3 가게 링크 분석

- **[확인 필요]** 네이버 지도와 캐치테이블의 가게 페이지를 프로그램으로 읽는 것이 각 서비스의 약관에서 허용되는지. 공식 API가 있다면 어떤 정보(이름, 주소, 업종, 메뉴, 사진, 영업시간)를 주는지.
- 허용 범위에 따라 세 가지 중 하나가 된다.

| 경우 | 구현 |
|---|---|
| 공식 API로 충분한 정보를 받을 수 있음 | API로 채운다 |
| 이름과 주소 정도만 받을 수 있음 | 받은 것만 채우고 나머지는 사장님이 입력한다. 소개 글은 `ContentDraftPort`로 초안을 만든다 |
| 받을 수 없음 | 링크 입력 단계를 "가게 이름으로 시작하기"로 바꾸고 사장님이 입력한다 |

- 2번 설계가 분석 실패 시 직접 입력으로 넘어가게 해 두었으므로, 어느 경우든 앱의 흐름은 유지된다.
- 가져온 사진은 서버가 저장소로 복사한다. **[확인 필요]** 그 사진을 가게 페이지에 쓰는 것의 저작권.

### 3.4 AI 콘텐츠 초안

- 쓰는 곳: 가게의 콘텐츠 초안(2번), 장면 흐름과 재협업 메시지(6번). 8번의 연락 메시지는 고정 틀로 만들고 LLM을 쓰지 않는다.
- 입력은 가게나 캠페인의 공개 정보뿐이다. 개인의 연락처나 대화 내용은 넣지 않는다.
- 출력은 정해진 구조(장면 목록, 본문)로 받고, 구조가 맞지 않으면 한 번 다시 요청한 뒤 실패로 처리한다. 실패하면 "지금은 초안을 만들 수 없어요. 잠시 뒤 다시 시도해 주세요."
- 하루 다시 만들기 10번(2번 설계) 외에, 전체 사용량의 월 상한을 설정값으로 둔다. 넘으면 초안 만들기를 멈추고 운영자에게 알린다.
- **[제안]** 어느 LLM을 쓸지는 정하지 않았다. 한국어 문안의 품질과 요금을 견본 문안으로 비교해 고른다.

### 3.5 결제와 지급

- **[확인 필요, 가장 중요]** 3번 설계 6장의 대금 보관 구조. PG사에 "판매자(크리에이터)에게 대금을 나눠 지급하는 서비스"가 있는지, 그 서비스를 쓰면 Cora가 대금을 직접 보관하지 않게 되는지를 PG 계약 상담에서 확인한다. 이 답에 따라 `PaymentPort`와 `PayoutPort`가 한 서비스의 두 기능이 되거나 따로가 된다.
- PG를 고를 때 필요한 기능: Flutter에서 쓸 수 있는 결제창, 카드·계좌이체·간편결제, 결제 통지(웹훅)와 서명 검증, 부분 환불(남은 금액 환급), 지급 대행, 계좌 실명 조회, 테스트 환경.
- 바꾸는 것: 앱의 가짜 결제창을 PG의 결제창으로, 서버의 통지 처리에 PG의 서명 검증을, 환급을 PG의 부분 취소로, 지급을 지급 대행으로. 3번 설계의 장부와 상태는 그대로다.
- 통지가 늦거나 빠질 때를 대비해, 결제 대기 상태가 10분을 넘으면 서버가 PG에 결제 상태를 물어 맞춘다.
- **[확인 필요]** 앱 안 결제와 스토어의 규정. 이 앱의 결제는 사람 사이의 실제 서비스(콘텐츠 제작) 대가라서 스토어의 앱 내 구매 의무 대상이 아닐 것으로 보지만, 심사 지침의 해당 조항을 확인하고 심사 메모에 설명을 넣는다.
- **[확인 필요]** 크리에이터 지급의 세금, 사장님에게 줄 증빙(3번 설계 6장).

### 3.6 인스타그램과 조회수

- `InstagramPort`와 `ViewCountPort`의 인스타그램 구현은 같은 연결을 쓴다. 크리에이터가 자기 계정을 연결해야 그 계정의 게시물과 성과를 읽을 수 있다.
- **[확인 필요]** Meta 앱 심사에서 받아야 할 권한의 정확한 이름과 조건, 개인 계정도 되는지 아니면 프로페셔널 계정이어야 하는지, 릴스의 조회수를 어떤 이름의 값으로 주는지. 심사에는 앱의 동작 영상과 개인정보 처리방침 주소가 필요하므로, 가짜 구현으로 흐름이 완성된 뒤 신청할 수 있다.
- 크리에이터가 프로페셔널 계정이 아니어서 연결할 수 없으면: 앱이 계정 전환 방법을 안내한다. 연결하지 못한 크리에이터는 조회수당 오퍼를 수락할 수 없다(공통 규칙 2장). 식사권만 있는 가게 오퍼와 브랜드 계약(고정 제작비)은 연결 없이 진행할 수 있다.
- 제출된 링크가 연결된 계정의 게시물인지 확인한다. 아니면 "내 계정의 게시물만 제출할 수 있어요."
- 유튜브 쇼츠의 조회수는 공개 값이라 크리에이터의 연결 없이 읽을 수 있을 것으로 본다. **[확인 필요]** 그 영상이 그 크리에이터의 것인지 확인하는 방법.
- 네이버 블로그 글은 조회수를 밖에서 읽을 수 없다. **[제안]** 블로그 글은 조회수당 지급을 고를 수 없게 한다(2번 설계의 보상 고르기에서 막는다).
- 연결 정보가 만료되면 크리에이터에게 다시 연결하라고 알린다. 집계 중인 협업이 있으면 3번 설계의 "3일 연속 읽지 못함" 규칙이 적용된다.

### 3.7 목록과 연락

- 8번 설계 2장의 기본안대로 `DirectoryPort`는 운영자가 올린 목록, `OutreachPort`는 `manual`이 실제 구현이다. 8번 설계 6장의 확인이 끝나야 운영 환경에서 켠다.
- 확인 결과 이 기능을 뺀다면: 사장님 홈의 "리스트 검색"과 찾기 탭의 "리스트" 전환을 숨기는 설정값 하나를 둔다. **[결정]**과 어긋나지 않게, 이것은 기능별 켜고 끄기 장치가 아니라 이 묶음 하나의 제외 스위치다.

## 4. 출시에 필요한데 캔버스에 없는 화면

- **회원 탈퇴.** 프로필 탭 → 설정 → "회원 탈퇴". 진행 중인 협업이나 보관 중인 금액이 있으면 막고 이유를 보여 준다. 탈퇴하면 프로필과 콘텐츠를 지우고, 장부와 계약은 법정 보관 기간 동안 남긴다. **[확인 필요]** 보관 기간.
- **약관과 개인정보 처리방침 동의.** 첫 로그인 뒤 한 화면: 이용약관(필수), 개인정보 처리방침(필수), 마케팅 알림(선택). 문서는 웹 주소로 연다. **[확인 필요]** 문서의 내용.
- **설정.** 로그아웃, 역할 바꾸기, 약관 보기, 문의하기, 앱 버전, 회원 탈퇴.
- **문의하기.** 1~8번 설계에서 운영자 이메일로 연결했다. 주소를 정해야 한다.
- **강제 업데이트 안내.** 서버가 지원하는 최소 앱 버전을 알려 주고, 낮으면 "업데이트가 필요해요"와 스토어 버튼만 보여 준다.
- **사업자 정보 표시.** **[확인 필요]** 앱 안에 사업자 정보(상호, 대표자, 사업자등록번호, 주소, 연락처)를 표시할 의무와 통신판매업 신고 대상 여부.

## 5. 운영 환경

기술 스택 설계에서 미정으로 남긴 것들이다.

### 서버 호스팅

필요한 조건: 항상 켜져 있는 프로세스(WebSocket과 작업 큐 때문에 요청이 올 때만 뜨는 방식은 맞지 않는다), 한국에서 가까운 지역, Docker 이미지로 배포, 환경변수의 안전한 보관, 무중단 배포.

- **[제안]** Supabase 프로젝트를 서울 지역에 만들고, 서버도 같은 지역이나 가장 가까운 지역에 둔다. DB와 서버가 멀면 모든 요청이 느려진다.
- **[제안]** 처음에는 서버 한 대(API, 게이트웨이, 작업 처리기를 한 프로세스로)로 시작한다. 5번 설계가 게이트웨이의 전달을 Redis로 거치게 해 두었으므로 나중에 여러 대로 늘릴 수 있다.
- 어느 호스팅 서비스를 쓸지는 정하지 않았다. 위 조건과 월 비용으로 고른다.

### 그 밖의 것

| 항목 | 설계 |
|---|---|
| Redis | 관리형 서비스. 작업 큐가 쓰므로 데이터가 재시작에도 남아야 한다 |
| 환경 | 개발, 스테이징, 운영 세 개. 셋 다 원격 Supabase 프로젝트를 따로 쓴다(개발용은 공통 기반에서 이미 만들었다). 스테이징은 PG와 Meta의 테스트 환경에 붙인다 |
| 배포 | `main`에 합쳐지면 스테이징에 자동 배포. 운영은 태그를 달 때 배포. DB 마이그레이션은 배포 단계에서 `DIRECT_URL`로 실행한다 |
| CI | 올릴 때마다 서버의 lint·test·e2e·DB 테스트, 앱의 analyze·test, 생성된 API 클라이언트가 최신인지 확인 |
| 앱 빌드 | 스토어에 올릴 빌드를 만드는 자동화. 서명 키는 CI의 비밀 값으로 둔다 |
| 오류 추적 | 서버와 앱의 오류를 한곳에서 본다. 개인정보와 토큰이 오류 보고에 실리지 않게 거른다 |
| 로그 | Wiki의 Security logging 기준. 결제·지급·권한 거부·로그인 실패를 남기고, 계좌번호·토큰·메시지 내용은 남기지 않는다 |
| 백업 | Supabase Pro의 일일 백업을 쓴다. 출시 전에 복구를 한 번 해 본다 |
| 사용 분석 | **[제안]** 첫 출시에는 넣지 않는다. 서버의 기록으로 가입·가게 공개·오퍼·수락·결제 수를 센다 |

## 6. 출시 전 점검

- 모든 `_ADAPTER` 환경변수가 `fake`가 아니다(서버가 스스로 확인한다).
- 운영 Supabase 프로젝트: 이메일 로그인 꺼짐, 모든 테이블 RLS 켜짐(`yarn test:db`를 운영 DB의 읽기 전용 연결로 실행), 서비스 역할 키가 앱에 없음.
- 운영 빌드: 가짜 인증(`AUTH_ADAPTER=fake`)과 모션 갤러리가 없음(가짜 인증이면 앱이 시작을 거부함), 가짜 결제창이 없음.
- Wiki의 Security baseline 점검표를 통과함.
- 실제 돈으로 처음부터 끝까지 한 번: 가게 등록 → 오퍼 → 수락 → 결제(최소 금액) → 링크 제출 → 집계 → 지급 → 환급. 장부의 합이 맞는지 확인한다.
- 두 플랫폼의 중저가 실기기에서 주요 화면의 전환이 끊기지 않음.
- 스토어 제출물: 앱 설명, 화면 사진, 개인정보 처리방침 주소, 심사용 계정(심사자가 로그인할 수 있는 휴대폰 번호·카카오·네이버 계정 또는 심사용 로그인 방법), 결제에 대한 설명 메모. **[확인 필요]** 심사자가 카카오 계정 없이 앱을 볼 방법.

## 7. 신청 순서 (제안)

대기 시간이 긴 것부터 신청한다. 구현은 승인 뒤에 한다.

1. **법률 확인 의뢰** — 대금 보관, 크리에이터 지급의 세금, 8번 설계의 목록과 연락. 결과가 PG 선택과 8번 기능의 유무를 정한다.
2. **PG 계약 상담과 심사** — 지급 대행 가능 여부를 먼저 묻는다.
3. **Apple·Google 개발자 계정, 카카오·네이버 개발자 앱, SMS 업체** — 사업자 명의로.
4. **Meta 앱 심사** — 가짜 구현으로 7번까지 완성돼 동작 영상을 찍을 수 있을 때.
5. **약관과 개인정보 처리방침 작성**
6. **서버 호스팅과 Redis 계약, 스테이징 환경 구성**
7. **스토어 심사 제출**

## 8. 소유자 확인이 필요한 것

1. **PG사 후보.** 정하지 않았다. 지급 대행이 되는 곳이 조건이다.
2. **법률 확인을 누구에게 맡길지.**
3. **서버 호스팅.** 조건만 정했다.
4. **LLM.** 정하지 않았다.
5. **링크 분석이 불가능할 때.** 링크 입력을 가게 이름 입력으로 바꾸는 것을 받아들일지. 회의에서 "링크만 넣으면"이 핵심 편의로 언급됐다.
6. **블로그 글의 조회수당 지급 제외.**
7. **운영자 이메일 주소, 사업자 정보.**

## 9. 답이 없을 때의 기본 결정

8장과 다른 설계의 확인 항목 가운데 기본값이 없던 것들이다. 소유자가 다르게 정하지 않으면 아래대로 진행한다. 모두 **[제안]**이다.

| 항목 | 기본 결정 | 바꿀 수 있는 시점 |
|---|---|---|
| 수수료율 | 가게 오퍼, 입찰, 브랜드 계약 모두 10%, 맡기는 쪽 부담. 식사권만 있는 오퍼는 수수료 없음 | 설정값이라 언제든 |
| PG사 | 지급 대행(판매자 정산)과 Flutter 결제창을 함께 제공하는 국내 PG 가운데, 계약 상담에서 대금 보관 구조에 대한 답을 먼저 주는 곳. 두 곳 이상에 동시에 상담을 넣는다 | 계약 전. `PaymentPort`와 `PayoutPort` 뒤에 있어 코드에는 영향이 없다 |
| 서버 호스팅 | Supabase 프로젝트와 같은 서울 지역의 컨테이너 호스팅. 서버 한 대, 항상 켜 둠 | 출시 뒤에도 가능. Docker 이미지로 배포하므로 옮기기 쉽다 |
| Redis | 서버와 같은 지역의 관리형 Redis | 출시 뒤에도 가능 |
| LLM | 스테이징에서 견본 가게 10곳의 초안을 두 가지 이상의 모델로 만들어 보고, 한국어 문안이 자연스러운 쪽 가운데 요금이 낮은 것 | `ContentDraftPort` 뒤에 있어 언제든 |
| 입찰의 뜻 | 입찰 금액 = 조회수당 지급의 상한 (공통 규칙 15장) | 7번 계획을 쓰기 전 |
| 8번 유입 전략 | 기본안(운영자가 고른 목록, 사장님이 직접 발송)으로 만든다. 법적 확인에서 막히면 `DIRECTORY_ENABLED=false`로 끄고 출시한다 | 법적 확인 뒤 |
| 링크 분석이 불가능할 때 | 받을 수 있는 정보만 채우고 나머지는 사장님이 입력한다 | 약관 확인 뒤 |
| 블로그 글 | 조회수당 지급을 고를 수 없다 | 언제든 |
| 운영자 이메일, 사업자 정보 | 설정값 `OPERATOR_EMAIL`과 앱의 설정 화면 문구로 둔다. 값은 출시 전에 소유자가 넣는다 | 출시 전 |

법률 확인이 필요한 항목(대금 보관, 지급의 세금, 전자 계약, 계정 목록과 연락)은 기본 결정을 둘 수 없다. 확인 결과가 나올 때까지 해당 실제 연동을 켜지 않는다.
