## 1. 무엇이, 왜 바뀌나

2026-11-12에 기획 캔버스가 바뀌었다. 가게 사장님 흐름은 "링크 → 페이지 → 오퍼 → 수락 → 결제"의 한 줄에서, 아래 네 가지가 더해진 모양이 됐다.

1. **보상을 숫자로 정한다.** 식사권과 현금을 따로 계산하고, 사장님이 낼 수 있는 가장 큰 돈("최대 현금 부담")을 먼저 보여 준다.
2. **조건을 주고받는다.** 크리에이터가 "내 방식으로 제안"할 수 있고, 보낸 조건은 판본으로 고정된다.
3. **결과를 보여 준다.** 7일 뒤에 조회 자료와 계산을 양쪽이 확인하고, 사장님은 평소 게시물과 비교한 결과를 본다.
4. **체험단에서 옮겨 오게 한다.** 체험단 후기 글을 가져오고, 재계약 전에 체험단과 비교해 보여 준다.

이미 구현한 2·3번 코드는 옛 규칙(조회 1회당 10원·상한 10만 원, 수락과 거절만 있는 오퍼, 7일째 즉시 정산)으로 돼 있다. 이 설계의 계획이 그 코드를 고친다.

### 하지 않는 것

- F5 AI 제작 주문과 "이번 주 가게 게시물"의 자동 초안 (AI 제작 계획)
- `cora.page` 주소로 열리는 실제 웹 페이지 (출시 준비 계획). 여기서는 주소 이름과 공유까지다.
- 브랜드 화면의 변경 (4~6번 설계에 반영한다). 다만 F1·F2·F3는 브랜드도 쓰므로, 받는 쪽이 캠페인 협업이어도 동작하게 만든다.
- 실제 링크 분석, 실제 조회수 읽기, 캡처의 자동 판독 (가짜 구현과 운영 명령으로 시작한다)

### 실패로 보는 것

- 옛 판본을 수락해 양쪽이 서로 다른 조건으로 알고 있게 되는 것
- 화면에 보인 "최대 현금 부담"보다 큰 돈이 결제되는 것
- 조회 자료가 확인되기 전에 돈이 나가거나, 0원으로 끝나는 것
- 이미 결제된 옛 협업의 금액이 개정으로 바뀌는 것

## 2. 핵심 구조

```text
사장님: 링크 하나(A2) 또는 직접 입력(F7) → 가게 페이지(A3) ─┬→ AI로 직접 제작(A4)
                                                          └→ 크리에이터 모집: 보상·예산(F1) → 검토(F2) → 가게 공개

크리에이터: 가게 상세(D2) ─┬→ 조건 그대로 지원 ─→ 사장님 홈: 지원자 추천 3명(G2) → 좋아요하고 오퍼(A5→F2)
                          └→ 내 방식으로 제안(F6→F2) ────────────┐
                                                                ▼
                         제안함(F3): 내가 응답할 차례 / 상대 대기 / 종료   ← 판본을 주고받음
                                                                │ 최신 판본 수락
                                                                ▼
                         결제(A8) → 보관(A7) → 링크 제출 → 7일 → 조회 자료 확인(F4) → 지급·환불 → 7일 결과(G1)
```

- **가게의 기본 조건 = 모집 조건.** 옛 "기본 오퍼 조건" 화면은 F1과 F2가 대신한다.
- **오퍼 = 제안.** 테이블은 `offers`를 그대로 쓰고 판본을 붙인다. 화면에서는 사장님이 보내는 것을 "오퍼", 주고받는 목록을 "제안함"이라고 부른다(캔버스 그대로).
- **지원과 제안은 다르다.** "조건 그대로 지원"은 조건을 건드리지 않는 관심 표시이고(옛 지원과 같다), "내 방식으로 제안"은 판본을 내는 것이다.

## 3. 화면별 동작

### A1 시작 · 역할 선택

- **[화면]** 아래에 "등록 없이 먼저 둘러보기"가 생겼다.
- 동작은 공통 규칙 23장이다. 역할 없이 브랜드 관점의 발견 화면(01)을 읽기만 한다.
- **[제안]** 4번 계획이 발견 화면을 만들기 전에는 이 버튼을 만들지 않는다. 4번 계획에 이 진입점을 더한다.

### A2 가게 링크 입력 (등록 1/3)

- **[화면]** 제목 "가게 링크 하나면 돼요." 설명 "네이버 지도, 캐치테이블, 인스타그램, 체험단 후기 글 중 무엇이든 괜찮아요. 가입 없이 먼저 볼 수 있어요."
- **[화면]** 입력란 네 개: 네이버 지도, 캐치테이블, "체험단 후기 글 · 선택 · 인스타 게시물로 바꿔 드려요", "인스타그램 · 선택". 요약 예: "메뉴 12개, 사진 34장, 후기 58개 찾음", "영업시간 찾음".
- **[화면]** 아래 안내 끝에 "링크가 없거나 안 열리면 직접 입력"(F7로 간다).
- 링크 하나만 있어도 "가게 페이지 만들기"가 켜진다(옛 설계와 같다). "2개 이상 넣으면 더 정확해요."는 없어졌다.
- **[제안]** 체험단 후기 글은 네이버 블로그와 티스토리 주소만 받는다. 종류 `REVIEW_POST`를 더한다. 분석 결과로 후기 수와 "손님들이 자주 한 말"(A3)을 얻고, 글 자체는 AI 제작 계획이 인스타 게시물 초안으로 바꾼다. 이 계획에서는 주소를 저장하고 요약만 보여 준다.
- **[제안]** "가입 없이 먼저 볼 수 있어요."는 화면 문구로만 둔다. 이 화면은 로그인과 역할 선택 뒤에 오므로 따로 만들 동작이 없다. 로그인 전에 가게 페이지를 보여 주려는 뜻이면 로그인 순서가 바뀌어야 한다(6장 1번).
- 분석이 실패하면 옛 설계의 "빈 가게 페이지로 넘어가기" 대신 F7로 보낸다.

### F7 매장 직접 입력 (등록 1/3)

- **[화면]** 안내 "링크에서 정보를 가져오지 못했어요. 아래만 채우면 계속할 수 있어요."
- **[화면]** 입력: 가게 이름, "지점 · 같은 이름의 가게가 2곳 있어요"(지점 이름과 동네를 보여 주고 하나를 고른다), 대표 메뉴와 가격, "가게 사진 올리기 (사용 권한이 있는 사진만)". 버튼 "가게 페이지 만들기".
- A2에서 직접 들어오면 안내 문구는 보이지 않는다 **[제안]**.
- **[제안]** 지점 목록은 가게 이름으로 `StoreLinkPort.findBranches(name)`를 불러 얻는다. 결과가 하나 이하면 지점 줄을 숨긴다. 가짜 구현은 "한그릇 라멘"에 성수점(성수동2가)과 합정점(합정동)을 돌려준다. 지점을 고르면 그 지점의 주소로 시·도와 구·군을 채운다.
- **[제안]** 필수는 가게 이름뿐이다. 사진은 5MB 이하 한 장(대표 사진)이다.

### A3 자동 생성된 가게 페이지 (등록 2/3)

- **[화면]** 가게 이름 아래에 "cora.page/l/hangeureut-ramen · 공개 페이지"와 "공유"가 생겼다(공통 규칙 23장).
- **[화면]** 소개 글 상자의 제목이 "이런 가게가 맞나요? · 탭해서 고치기"가 됐고, 내용은 꼬리표와 후기 요약이다: "#진한국물 #바좌석 #조용한오후 · 손님들이 자주 한 말: “국물이 진해요”, “혼밥하기 좋아요”. 공개 페이지에는 크리에이터 지원하기 버튼이 보여요."
- **[화면]** 버튼이 둘이 됐다: "AI로 직접 제작"(A4), "크리에이터 모집"(F1). "정보 고치기"와 "이대로 다음"은 없어졌다.
- 각 항목을 눌러 그 자리에서 고친다. 옛 편집 화면은 항목을 눌렀을 때 여는 화면으로 남긴다 **[제안]**.
- **[제안]** 가게에 더하는 값: 꼬리표(최대 5개, 각 10자), "손님들이 자주 한 말"(최대 3개, 각 20자), 주소 이름. 링크 분석이 채우고 사장님이 고칠 수 있다. 옛 소개 글은 D2에 계속 보이므로 지우지 않는다.
- 주소 이름은 가게를 처음 저장할 때 만들고 바꾸지 않는다. 공개 전의 가게도 주소 이름은 가진다. 공유는 가게가 공개된 뒤에만 켜진다 **[제안]**.

### A4 AI 콘텐츠 초안 (등록 3/3)

- **[화면]** 버튼이 "가게 계정에 올리기"(F5)와 "오퍼 만들기"(A5)로 바뀌었다. "다시 만들기"는 위로 올라갔다.
- "가게 계정에 올리기"는 AI 제작 계획이 만든다. 그 전에는 "준비 중이에요"로 간다.
- 등록 중에 A4에서 "오퍼 만들기"를 누르면 F1(모집 조건)로 간다. 가게가 이미 공개돼 있으면 A5로 간다 **[제안]**.

### F1 보상·예산 설정 (제안 만들기 2/3)

- **[화면]** 제목 "보상을 정해요." 설명 "식사권과 현금은 따로 계산해요."
- **[화면]** 줄 세 개:
  - 제공 혜택 · "현금과 더하지 않아요" · "식사권 40,000원 · 2인"
  - 고정 현금 (선택) · 고르는 값: 없음, 금액들
  - 조회수 수당 · "조회수만큼 더 드려요 · 기본으로 켜져 있어요" · 단가 "1,000회당 2,000원", 1인 상한 "최대 60,000원", 측정 기간 "게시 후 7일"
- **[화면]** 아래 고정: "최대 현금 부담 · 남으면 환불"과 금액, 버튼 "검토하고 보내기".
- 값의 뜻과 계산은 공통 규칙 2장이다.
- **[제안]** 제공 혜택 줄을 누르면 이름, 금액, 인원을 고친다(옛 "식사권 고치기"). 혜택을 "없음"으로 둘 수도 있다.
- **[화면]** 고정 현금의 선택지는 없음, 3만 원, 5만 원, 10만 원이다. **[제안]** 여기에 직접 입력을 더한다. 직접 입력(1만 원 단위, 최대 100만 원)이다. 브랜드가 쓸 때의 최대값은 4번 설계의 제작비 범위(최대 1,000만 원)를 따른다. 최대값은 맡기는 쪽의 종류별 서버 설정으로 둔다.
- **[제안]** 단가와 1인 상한 줄을 누르면 공통 규칙 2장의 범위 안에서 고른다. 측정 기간은 고칠 수 없다.
- **[제안]** 세 요소가 모두 없으면(혜택 없음, 고정 현금 없음, 수당 꺼짐) 버튼이 꺼지고 "보상을 하나 이상 정해 주세요."를 보여 준다.
- 쓰이는 곳이 셋이다. 머리글은 모두 "제안 만들기"다.

| 들어온 곳 | 받는 사람 | 마지막 버튼(F2) |
|---|---|---|
| A3 "크리에이터 모집", 등록 중의 A4 | 없음 (모집 조건) | "이 조건으로 공개하기" **[제안]** |
| A5의 "자세히 설정", G1 "다시 만나기", 15 "새 제안 만들기" | 크리에이터 한 명 | "이 조건으로 보내기" |
| F3에서 역제안에 "응답하기" → 고쳐서 다시 보내기 | 그 제안의 상대 | "이 조건으로 보내기" |

- 단계 표시 "2 / 3"의 1단계는 결과물 고르기다. 모집 조건과 새 오퍼에서는 A5의 1단계(형식 고르기)가 1단계 역할을 한다 **[제안]**.

### F2 제안 보내기 전 검토 (제안 만들기 3/3)

- **[화면]** 제목 "받는 사람과 조건을 한 번 더 확인해요."
- **[화면]** 줄: 받는 사람, 모집("한그릇 라멘 · 첫 숟가락 릴스"), 결과물("릴스 1편 · 30초 안팎"), 제공 혜택, 고정 현금, 조회수 수당("1,000회당 2,000원 · 1인 최대 60,000원"), 사용권("가게 계정 재게시 3개월"), 최대 현금 부담.
- **[화면]** 안내 "보낸다고 합의가 되는 건 아니에요. 상대가 수락하면 그때 결제해요. 보낸 조건은 판본 1로 고정되고, 이용료 [수수료]는 별도예요." 버튼 "고치기", "이 조건으로 보내기".
- "[수수료]" 자리에는 서버가 내려 준 수수료율로 계산한 금액을 넣는다. 안내의 "판본 1"은 이번에 만들어질 판본 번호로 바꾼다.
- **[제안]** "모집" 줄은 가게 이름과 가게의 모집 한 줄이다. 모집 한 줄은 가게의 새 값(40자)이고, 비어 있으면 가게 이름만 보인다.
- **[제안]** 사용권의 선택지: 가게 계정 재게시 3개월(기본), 가게 계정 재게시 6개월, 사용 안 함. 줄을 눌러 고친다.
- **[제안]** 모집 조건을 정할 때는 "받는 사람" 줄이 "공개 모집"이고, 안내는 "크리에이터가 가게 페이지에서 이 조건을 봐요. 오퍼를 보낼 때 바꿀 수 있어요."다. 누르면 가게가 공개되고 사장님 홈으로 간다.
- 크리에이터가 F6에서 넘어오면 받는 사람은 가게다. 사장님이 보내면 "오퍼를 보냈어요."와 함께 F3로 간다.

### A5 오퍼 보내기

- **[화면]** 2단계 설명이 "가게 등록 때 정한 기본값이에요. 최대 현금 부담 60,000원, 조회수가 적으면 남은 돈은 돌려드려요."가 되고 "자세히 설정"(F1)이 붙었다.

### F6 크리에이터 역제안

### F3 제안함

- **[화면]** 탭 "진행 중 N" / "종료 N". 진행 중은 "내가 응답할 차례"와 "상대 대기"로 묶는다.

- 브랜드도 같은 화면을 쓴다(07의 "남은 캠페인 예산"에서 들어온다). 브랜드의 줄은 캠페인 협업의 조건 버전이다. 5번 설계가 채운다.

### F4 조회 자료와 보상 계산

- **[화면]** 머리 "성과 확인" 옆에 "안" 표시가 붙어 있다. 소유자가 이 화면이 확정됐다고 확인했다(2026-11-12 소유자 결정). "안"은 캔버스에 남은 초안 표시로 보고 앱에는 넣지 않는다 **[제안]**.
- **[화면]** 위 상자: "조회 자료", 상태 표지(미확인 / 확인 완료 / 이의 제기됨), "12,500회".

- **[화면]** "보상 계산": 조회수 수당("12,500회 × 1,000회당 2,000원 = 25,000원"), 1인 상한("60,000원 · 상한 안"), 사장님께 환불("35,000원"), 크리에이터 지급 예정("25,000원").

- **[제안]** 자료 출처 줄의 글: 연결 계정에서 읽었으면 "연결 계정", 캡처를 올렸고 운영자가 아직 보지 않았으면 "캡처 제출 · 확인 중", 확인됐으면 "캡처 제출 · 확인됨". 캔버스의 "연결 계정 · 캡처 제출 중 확정 예정"은 두 값을 함께 적은 견본으로 본다.
- **[제안]** 상한을 넘었으면 1인 상한 줄이 "60,000원 · 상한 적용"이 된다. 고정 현금이 있으면 "고정 현금" 줄을 더하고 "크리에이터 지급 예정"은 합계다.

### G1 7일 결과 · 사장님

- **[화면]** 머리 "7일 결과". "{활동 이름} · 릴스 · 11월 4일 게시", 큰 숫자 "12,500회".
- **[화면]** "우리 가게 평소 게시물 대비 3.1배", "평소 약 4,000회", 막대 두 개(평소, 이번).
- **[화면]** "크리에이터 지급 25,000원", "사장님께 환불 35,000원", "집계 출처와 계산 보기"(F4).
- **[화면]** 버튼: "새 오퍼"(A5), "영상 받기", "{활동 이름}과 다시 만나기"(F1).
- 들어오는 곳: 정산 완료 알림, 사장님 쪽 진행 화면의 끝난 협업 **[제안]**.
- **[제안]** "평소"는 가게 인스타그램 계정의 최근 게시물 평균 조회수다. `ViewCountPort.readAccountAverage(instagramHandle)`를 더한다. 가짜 구현은 4,000을 돌려준다. 가게가 인스타그램 링크를 넣지 않았거나 읽지 못하면 비교 상자를 숨기고 조회수만 보여 준다. 평소 값은 결과를 처음 만들 때 한 번 읽어 저장한다.
- **[제안]** 배수는 소수 첫째 자리까지 내림한다.
- **[제안]** "새 오퍼"는 그 크리에이터가 받는 사람으로 채워진 A5를 연다. G3의 "다음 달은 Cora로 오퍼 보내기"와 공개된 뒤 A4의 "오퍼 만들기"는 받는 사람이 정해지지 않았으므로 지원자 추천(G2)으로, 새 지원이 없으면 사장님 홈의 지원자 탭으로 간다.
- **[제안]** "영상 받기"는 캔버스에서 F5(AI 제작)로 이어진다. 뜻이 화면만으로는 분명하지 않다(6장 2번). 이 계획에서는 크리에이터가 제출한 게시 링크를 여는 동작으로 만들고, AI 제작 계획이 캔버스대로 바꾼다.
- 조회수 수당이 없던 협업은 조회수를 세지 않는다(공통 규칙 2장). 그래서 큰 조회수 숫자와 평소 대비 상자가 없고, 지급과 환불 줄 대신 "고정 현금 {금액}원 지급"만 보여 준다 **[제안]**. 제공 혜택만 있던 협업에는 G1을 만들지 않는다.

## 4. 상태와 규칙

### 오퍼 (제안)

```text
SENT ──(최신 판본 수락)──→ ACCEPTED ──→ 결제 (3번)
  │  ↺ 새 판본 (차례가 바뀌고 응답 기한 7일을 다시 셈)
  ├──→ DECLINED   (받은 쪽이 거절 또는 종료)
  ├──→ CANCELLED  (보낸 쪽이 취소 또는 종료)
  └──→ EXPIRED    (응답 기한 7일)
```

- 상태 값은 옛 것을 그대로 쓴다. 더하는 것: 최신 판본 번호, 응답할 차례(가게 / 크리에이터), 시작한 쪽, 종료 사유.
- `DECLINED`와 `CANCELLED`의 구분은 "최신 판본을 쓴 쪽이 끝냈는가"다. 쓴 쪽이 끝내면 `CANCELLED`, 받은 쪽이 끝내면 `DECLINED`.
- 한 가게와 한 크리에이터 사이에 열린 오퍼(`SENT`, `ACCEPTED`)는 하나다(옛 규칙). 크리에이터가 F6으로 시작해도 이 규칙이 적용된다. 이미 열린 오퍼가 있으면 F6은 그 오퍼의 다음 판본을 낸다.
- 수락은 차례인 쪽만 한다. 판본 번호가 최신이 아니면 409 `STALE_VERSION`.
- 수락되면 그 판본의 값이 협업의 조건 사본이 된다. 사장님이 크리에이터의 역제안을 수락한 경우에도 크리에이터에게 다시 묻지 않는다(자기가 쓴 판본이다).
- 수락 후 결제 기한 3일, 결제 전 취소는 옛 규칙 그대로다.

### 지원

- 상태는 옛 것 그대로다. 더하는 것: 한 줄(100자), "추천에서 넘김" 표시.
- 크리에이터가 "내 방식으로 제안"을 보내면 살아 있는 지원이 없을 때 지원을 함께 만들고 바로 `OFFERED`로 둔다(오퍼에 연결). 그래서 "새 지원" 숫자에는 들지 않고 제안함에 나온다.

### 정산

- 측정 기간이 끝난 날: 조회수 수당이 켜져 있으면 계산을 만들고 `미확인`으로 둔다. 꺼져 있으면 바로 확정한다.
- 확인 완료가 되면: 장부를 옮기고(고정 현금과 조회수 수당 지급액 → 크리에이터 지급, 남은 상한 → 가게 환불), 협업을 `SETTLED`로 바꾸고, 송금은 다음 주 수요일이다.
- 이의 제기와 캡처는 공통 규칙 21장이다.
- 이미 `SETTLED`이거나 결제가 끝난(`FUNDED`, `COUNTING`) 옛 협업은 결제할 때 저장한 값으로 끝까지 간다. 옮길 때 단가만 "1,000회당"으로 바꿔 저장한다(조회 1회당 10원 → 1,000회당 10,000원). 금액은 바뀌지 않는다.

### 알림

더하거나 바꾸는 것이다. 모두 `NotificationsService`를 거친다.

| 사건 | 받는 사람 | 문구 **[제안]** |
|---|---|---|
| 역제안 도착 | 사장님 | "{활동 이름}님이 조건을 바꿔 제안했어요." |
| 새 판본 도착 | 크리에이터 | "{가게 이름}이 조건을 바꿔 다시 보냈어요." |
| 제안 수락 (사장님이 역제안을 수락) | 크리에이터 | "{가게 이름}이 제안을 수락했어요. 결제하면 알려드릴게요." |
| 제안 종료 | 상대 | "{이름}님과의 제안이 종료됐어요." |
| 집계 끝, 확인 요청 | 사장님 | "조회수 집계가 끝났어요. 자료를 확인해 주세요." |
| 집계 끝 | 크리에이터 | "조회수 집계가 끝났어요. 계산을 확인해 보세요." |
| 캡처 요청 | 크리에이터 | "조회수를 읽지 못했어요. 인사이트 캡처를 올려 주세요." |
| 이의 제기됨 | 상대 | "조회 자료에 이의가 제기됐어요. 운영팀이 확인하고 연락드릴게요." |

- 옛 "정산 완료(사장님): 조회수 집계가 끝났어요. {금액}원을 돌려드려요."는 확인 완료 때 보내고, 누르면 G1이 열린다. 돌려줄 돈이 0원이어도 금액 문장을 뺀 알림을 보낸다(G1로 가는 길이 이것뿐이다).
- 새 알림은 모두 협업 탭에 들어가고 끌 수 없다 **[제안]**. 계정·알림 설계 3.2 표에는 계획을 실행할 때 줄을 더한다.

## 5. 데이터와 서버 (윤곽)

정확한 스키마와 엔드포인트는 실행 계획에서 정한다. 새 테이블에는 RLS를 켜고 정책을 만들지 않는다.

| 바뀌는 곳 | 내용 |
|---|---|
| `stores` | 주소 이름(유일), 꼬리표, 손님들이 자주 한 말, 모집 한 줄, 모집 조건의 보상 세 요소와 사용권, 체험단 정보(월 금액, 종료일, 글 수), 평소 조회수 |
| `store_source_links` | 종류에 `REVIEW_POST` 추가 |
| `offers` | 최신 판본 번호, 응답할 차례, 시작한 쪽, 종료 사유. 보상 사본 칸은 판본으로 옮긴다 |
| `offer_versions` (새로) | 오퍼, 번호, 쓴 쪽, 결과물, 보상 세 요소, 사용권, 아이디어, 표현 원칙, 시리즈 사본 |
| `applications` | 한 줄, 추천에서 넘김 |
| `creator_series` (새로) | 크리에이터, 이름, 형식, 설명 |
| `collaborations`, `payments` | 조건 사본에 고정 현금과 사용권, 단가를 1,000회당으로 |
| `settlements` | 확인 상태(미확인 / 확인 완료 / 이의 제기됨), 확인 기한, 자료 출처, 고정 현금 지급액, 평소 대비 배수 |
| `view_evidences` (새로) | 협업, 캡처 파일, 적어 낸 조회수, 운영자 확인 여부 |
| `settlement_disputes` (새로) | 협업, 제기한 쪽, 사유, 처리 결과 |

### 서버가 하는 일

| 모듈 | 더하는 일 |
|---|---|
| `stores` | 직접 입력으로 만들기, 지점 찾기, 주소 이름 만들기, 모집 조건 저장과 공개, 체험단 정보 저장, 석 달 비교 계산 |
| `offers` | 판본 내기(양쪽), 판본 번호를 받는 수락, 종료와 사유, 제안함 목록(차례별), 제안 상세 |
| `applications` | 한 줄 저장, 추천 3명 계산, 추천에서 넘기기 |
| `creators` | 시리즈 만들기와 목록 |
| `payments` | 결제 금액을 최대 현금 부담으로 계산 |
| `settlements` | 계산 만들기와 미확인 상태, 확인, 48시간 뒤 자동 확인, 이의 제기, 캡처 받기, 7일 결과 |
| `ops` (운영 명령) | 캡처 확인(`confirm-evidence`), 조회수 고쳐 확정(`resolve-dispute`) |
| `config` | `GET /config`를 이 계획이 처음 만든다(지금 코드에 없다). 단가와 상한의 범위, 고정 현금 최대값, 수수료율을 내려 준다. 8번 계획과 AI 제작 계획은 여기에 값을 더한다 |

### 연동 포트

- `StoreLinkPort`: `findBranches(name)`를 더한다. `analyze`의 결과에 후기 수, 꼬리표, 손님들이 자주 한 말을 더한다.
- `ViewCountPort`: `readAccountAverage(handle)`를 더한다.
- 새 환경변수는 없다.

### 작업 큐

| 작업 | 시점 |
|---|---|
| 조회 자료 자동 확인 | 계산이 만들어지고 48시간 뒤 |
| 캡처 요청 | 조회수를 3일 연속 읽지 못한 때 |
| 캡처 미제출 멈춤 | 측정 기간이 끝나고 3일 뒤 |
| 제안 응답 기한 만료 | 최신 판본이 나오고 7일 뒤 (판본이 바뀌면 옛 작업은 아무 일도 하지 않는다) |

### 권한

- 판본은 그 오퍼의 두 당사자만 읽는다. 판본 내기와 수락, 종료는 당사자만 하고, 수락은 차례인 쪽만 한다.
- F4와 G1은 그 협업의 당사자만 읽는다. G1과 G3는 사장님만 읽는다.
- 캡처 파일은 서명된 주소로 올리고, 읽는 것은 당사자와 운영 명령뿐이다.
- 다른 사람의 것을 ID로 요청하면 404다(옛 규칙).
- 피하는 업종 필터(공통 규칙 3장)는 F6에도 적용된다. 다만 크리에이터의 협업 원칙은 4번 계획에서 생기므로, 이 필터와 G2 점수의 "받고 싶은 분야"는 4번 계획이 건다. 이 계획에서 G2의 분야 점수는 "주로 만드는 콘텐츠"로만 계산한다.

## 6. 소유자 확인이 필요한 것

중요한 순서다. 답이 없으면 **[제안]**대로 진행한다.

1. **"가입 없이 먼저 볼 수 있어요"(A2).** 로그인 전에 가게 페이지를 만들어 보여 주려는 뜻인지. 그렇다면 로그인(E1, E2)을 가게 페이지 뒤로 옮겨야 하고, 로그인하지 않은 사람이 링크 분석을 쓰게 된다. 지금은 문구만 넣었다.
2. **"영상 받기"(G1).** 크리에이터가 만든 영상 파일을 사장님이 받는 것인지, AI 제작으로 이어지는 것인지. 영상 파일을 받으려면 크리에이터가 원본을 올리는 단계와 사용권 확인이 필요하다.
3. **지원자 추천의 이유.** "가게 사진과 분위기가 비슷해요", "평균 2시간 안에 답장", "걸어서 8분"을 실제로 계산할지. 사진 분석, 응답 시간 기록, 위치 정보가 각각 필요하다. 지금은 지역, 분야, 지난 협업으로만 만든다.
4. **조회 자료 확인 기간.** 48시간 동안 이의가 없으면 자동 확인하는 것이 맞는지. 길수록 지급이 늦어진다.
5. **고를 수 있는 범위.** 단가 1,000~5,000원, 상한 1만~30만 원, 고정 현금 최대 100만 원.
6. **사용권.** 가게 오퍼의 기본값 "가게 계정 재게시 3개월"과 선택지(6개월, 사용 안 함).
7. **체험단 비교.** 사장님이 직접 넣은 금액과 글 수로 비교하는 것이 맞는지. 체험단 쪽 숫자는 확인할 길이 없다.
8. **F4의 "안" 표시.** 정해졌다: F4와 F5는 확정된 화면이다(2026-11-12 소유자 결정). F4 작업을 미루지 않고 계획대로 만든다. 남은 확인은 "안" 글자를 앱에 넣지 않는 것이 맞는지뿐이다.

## 7. 만드는 사람에게 맡기는 것

- 테이블의 정확한 컬럼과 인덱스, 엔드포인트 경로와 DTO, `SettlementMethod`에 더하는 값의 이름
- 옛 `offers`의 보상 사본을 판본 1로 옮기는 마이그레이션의 모양
- 제안 상세 화면과 캡처 올리기 화면의 배치 (캔버스의 토큰과 공용 위젯을 따른다)
- F1을 세 곳에서 쓰는 방법 (화면 하나에 인자, 또는 공용 위젯)
