## 1. 무엇을, 왜

서로 관심이 닿은 브랜드와 크리에이터가 대화하고, 조건을 버전으로 고쳐 가며 합의하고, 양쪽이 동의해 계약을 맺는다. 계약이 맺어지면 제작(6번)이 시작된다.

- **[화면]** "합의 기록과 최종 계약 체결은 별도예요." 조건에 서로 확인한 것과 계약에 동의한 것은 다른 단계다.
- **[화면]** "수락하기 전에는 내 추가 연락처가 공개되지 않아요." 대화는 받는 쪽이 수락해야 열린다.

### 하지 않는 것

- 사진·영상 파일을 대화로 보내기. 보낼 수 있는 것은 글, 내 콘텐츠 카드, 조건 수정 제안뿐이다.
- 읽음 표시, 입력 중 표시, 메시지 삭제와 수정
- 계약서 PDF 내려받기. 앱 안의 화면으로만 보여 준다.
- 운영자용 신고 처리 화면

### 실패로 보는 것

- 대화방에 들어 있지 않은 사람이 메시지를 읽거나 보낼 수 있는 것
- 합의한 조건과 다른 내용으로 계약이 맺어지는 것
- 한쪽만 동의했는데 계약이 체결된 것으로 보이는 것
- 메시지가 사라지거나 순서가 뒤바뀌는 것

## 2. 화면별 동작

### 10 콘텐츠 기반 제안 (크리에이터가 받음)

- **[화면]** "받은 제안", 브랜드 이름, "내 콘텐츠 「매일 손이 가는 물건들」에 제안했어요", "브랜드가 좋아한 점"과 브랜드가 쓴 글, 제작비와 형식, 입력란 "내가 만들고 싶은 콘텐츠 한 줄", "관심 보내기", "조건부터 질문하기".
- **[제안]** 브랜드가 발견 화면에서 관심을 보낼 때 "좋아한 점"을 한 줄 쓸 수 있다(선택). 글을 쓴 관심이 크리에이터에게 "받은 제안"으로 보인다. 글이 없는 관심은 추천 순서에만 반영된다.
- **[제안]** "관심 보내기"는 4번 설계의 관심과 같다(서로 관심이 된다). 입력한 한 줄은 조건 초안의 콘텐츠 제목이 된다.
- **[제안]** "조건부터 질문하기"는 서로 관심을 만들지 않고 브랜드에게 메시지 요청을 보낸다.
- **[제안]** 받은 제안은 크리에이터의 "관심" 탭 맨 위에 모인다.

### 11 메시지 요청

- **[화면]** "메시지 요청", 보낸 쪽 이름과 캠페인, 첫 메시지와 시각, 요약(제작물, 제작비, 촬영), 안내, "거절", "대화 수락".
- **[제안]** 대화가 열리는 경우는 세 가지다.

| 경우 | 수락이 필요한가 |
|---|---|
| 서로 관심이 닿음 | 아니오. 바로 열린다. |
| 가게 오퍼가 수락됨 | 아니오. 바로 열린다. |
| "조건부터 질문하기" | 예. 브랜드가 수락해야 열린다. |

- **[제안]** 캔버스의 이 화면은 크리에이터가 받는 모습이다. 브랜드가 서로 관심 없이 크리에이터에게 먼저 말을 거는 경로는 만들지 않는다(관심을 보내는 것으로 충분하다).
- **[제안]** 요청에는 첫 메시지 한 개만 담긴다. 거절하면 요청이 사라지고 보낸 쪽에는 "대화가 열리지 않았어요."로만 보인다. 같은 상대에게 다시 요청할 수 없다.

### D3 대화방

- **[화면]** 머리: 상대 이름, 캠페인 이름, 조건 요약 한 줄(예: "릴스 1편, 35만 원 + 제품, 11월 23일 시작"), 상태 한 줄(예: "조건 버전 2 · 브랜드 확인 대기"). 날짜 구분선, 말풍선, 콘텐츠 카드.
- **[화면]** 입력란 옆 더하기 버튼: "내 콘텐츠 카드", "조건 수정 제안". 오른쪽 위 메뉴: "알림 끄기", "차단하기", "신고하기".
- **[제안]** 머리의 조건 요약을 누르면 12 조건 합의 화면이 열린다.
- **[제안]** 조건 버전이 새로 생기거나 한쪽이 확인하면 대화에 안내 줄이 끼어든다. 예: "{이름}님이 조건 버전 2를 제안했어요.", "양쪽이 조건 버전 2를 확인했어요."
- **[제안]** 메시지는 한 개에 1,000자까지. 보내기에 실패하면 말풍선에 "다시 보내기"가 붙는다.
- **[제안]** 대화 목록(하단 메뉴 "대화"): 상대 사진과 이름, 마지막 메시지, 시각, 안 읽은 수. 메시지 요청은 목록 맨 위에 따로 모인다.
- **[제안]** 가게 오퍼의 대화방은 머리에 가게 이름과 오퍼 조건을 보여 준다. 조건 수정 제안은 없다(가게 오퍼는 조건을 바꾸지 않는다. 바꾸려면 취소하고 다시 보낸다).

### 차단과 신고

- **[제안]** 차단: 확인 후 그 대화방에서 양쪽 모두 메시지를 보낼 수 없게 된다. 상대에게는 "대화가 종료됐어요."로만 보인다. 차단한 상대는 추천에도 나오지 않는다. 진행 중인 협업이 있으면 차단할 수 없고 "진행 중인 협업이 있어요. 문의하기로 알려 주세요."를 보여 준다.
- **[제안]** 신고: 사유 하나(광고·스팸, 부적절한 말, 사기 의심, 기타)와 선택 설명. 저장하고 운영자 이메일로 알린다. 신고자에게 "신고를 접수했어요."
- **[제안]** 알림 끄기: 그 대화방의 푸시만 끈다.

### 12 조건 합의·변경 기록

- **[화면]** "조건 합의", "버전 2", 상태 "브랜드 확인 대기 중", 양쪽 표시 "나 · 확인함", "브랜드 · 대기".
- **[화면]** "대화에서 정한 조건", "초록색은 이번 버전에서 바뀐 조건이에요." 바뀐 항목은 새 값 아래에 "{이전 값}에서 변경".
- **[화면]** 항목: 제작비, 제작 시작, 제작물, 제품 제공, 수정 범위, 활용 권한, 지급 조건, 광고 표시.
- **[화면]** 변경 기록: "버전 1 · 브랜드의 최초 제안", "버전 2 · 내가 제작비·일정 수정 제안".
- **[화면]** "수정 제안", "계약서 미리 보기".
- **[제안]** 수정 제안 화면: 여덟 항목 중 광고 표시를 뺀 일곱 항목을 고칠 수 있다. 하나 이상 바꿔야 "제안 보내기"가 켜진다. 보내면 새 버전이 되고, 제안한 사람은 자동으로 "확인함"이 된다.
- **[제안]** 상대는 그 버전을 "확인"하거나 다시 "수정 제안"한다. 양쪽이 같은 버전을 확인하면 "합의됨"이 되고 "계약서 미리 보기"가 "계약하러 가기"로 바뀐다.
- **[제안]** 새 버전이 나오면 이전 버전의 확인은 무효다. 버전은 고치지 않고 쌓기만 한다.
- **[제안]** 고칠 수 있는 값의 형태:

| 항목 | 형태 |
|---|---|
| 제작비 | 1만 원 단위 금액 |
| 제작 시작 | 날짜 (오늘 이후) |
| 제작물 | 형식 네 가지 중 하나와 편 수 1~3 |
| 제품 제공 | 포함 / 미포함 |
| 수정 범위 | 없음 / 기획안 기준 1회 / 초안 기준 1회 / 초안 기준 2회 |
| 활용 권한 | 브랜드 계정 재게시만 / 광고 소재로도 사용 / 사용 안 함 |
| 지급 조건 | 게시 후 7일 이내 / 게시 후 14일 이내 |
| 광고 표시 | 고정 "영상·게시물에 명확히" |

### D4 최종 계약

- **[화면]** "협업 계약", "합의한 버전 2로 계약해요.", "양쪽이 모두 동의하면 계약이 체결되고 제작이 시작돼요." 양쪽 이름, 요약(제작물, 제작비, 제작 시작, 지급).
- **[화면]** 확인란 세 개: "합의한 조건 버전 {n}을 확인했어요", "광고 표시 의무를 지킬게요", "콘텐츠는 브랜드 계정 재게시에만 쓰여요". 다 확인해야 "동의하고 계약하기"가 켜진다. 그 전에는 "모두 확인하면 계약할 수 있어요".
- **[화면]** 한쪽만 동의하면 "브랜드 동의를 기다리고 있어요. 계약서는 체결 후 보관함에 저장돼요."
- **[제안]** 셋째 확인란의 문구는 합의한 "활용 권한" 값에 따라 바뀐다.
- **[제안]** 브랜드 쪽의 둘째 확인란은 "광고 표시를 요청할게요"다.
- **[제안]** 한쪽이 동의한 뒤 조건이 새 버전으로 바뀌면 그 동의는 취소된다.
- **[제안]** 계약이 체결되면 양쪽에 알림 "계약이 체결됐어요. 이제 제작을 시작할 수 있어요." 계약 내용은 6번 설계의 보관함과 협업 화면에서 다시 볼 수 있다.

### 브랜드의 결제 (캔버스에 없음)

- **[제안]** 브랜드가 계약에 동의할 때 제작비를 결제해 보관을 맡긴다. 3번 설계의 결제 모듈을 그대로 쓴다. 결제할 금액 = 제작비 + 서비스 수수료.
- **[제안]** 순서는 고정이다: 크리에이터 동의 → 브랜드 동의와 결제 → 결제가 승인되는 순간 계약 체결. 크리에이터가 동의하기 전에는 브랜드의 "동의하고 계약하기"가 꺼져 있고 "크리에이터의 동의를 기다리고 있어요."가 보인다. 결제는 했는데 계약이 안 된 기간이 없으므로 환급 규칙이 필요 없다(공통 규칙 2장).
- **[제안]** 지급: 게시 링크 제출 뒤 정확히 7일째 또는 14일째(합의한 지급 조건)에 제작비 전액을 지급한다. 조회수 집계는 하지 않는다. 계약 뒤에는 조건을 바꿀 수 없다.

## 3. 규칙

- 대화방은 당사자 두 명만 읽고 쓴다. 서버가 메시지마다 보낸 사람이 그 방의 참가자인지 확인한다.
- 메시지는 서버가 받은 순서로 번호를 매긴다. 앱은 번호 순으로 보여 주고, 다시 연결되면 마지막으로 받은 번호 뒤를 요청한다.
- 조건 버전과 계약 동의는 2번 설계의 오퍼처럼 조건부 갱신으로 처리한다. 동시에 들어온 두 수정 제안 중 하나만 다음 버전이 되고 다른 하나는 409를 받는다.
- 계약은 "합의됨" 상태의 버전으로만 만들 수 있다. 계약에는 그 버전의 조건 사본, 양쪽의 동의 시각, 각자 확인한 문구가 저장된다. 체결된 계약은 고치지 않는다.
- 앱은 전화번호와 이메일을 상대에게 보여 주지 않는다. 인스타그램 아이디는 공개 프로필 정보다(공통 규칙 10장).

## 4. 데이터와 서버 (윤곽)

| 테이블 | 담는 것 |
|---|---|
| `conversations` | 협업 또는 메시지 요청과 연결, 참가자 둘, 상태(요청·열림·거절·종료) |
| `messages` | 대화, 번호, 보낸 사람(안내 줄이면 없음), 종류(글·콘텐츠 카드·조건 안내), 내용 |
| `conversation_members` | 대화, 사용자, 마지막으로 읽은 번호, 알림 끔 |
| `blocks`, `reports` | 누가 누구를, 사유, 설명 |
| `terms_versions` | 협업, 버전 번호, 제안한 사람, 여덟 항목, 양쪽 확인 시각 |
| `contracts` | 협업, 합의한 버전, 조건 사본, 양쪽 동의 시각과 확인 문구, 체결 시각 |

### 실시간 전달

- NestJS WebSocket 게이트웨이. 연결할 때 Supabase 토큰을 검증한다. 토큰이 만료되면 연결을 끊고 앱이 새 토큰으로 다시 붙는다.
- 메시지를 보내는 것은 REST 요청으로 한다(실패와 재시도를 다루기 쉽다). 게이트웨이는 새 메시지와 조건 변경을 참가자에게 밀어 주는 역할만 한다.
- 앱이 꺼져 있거나 연결이 없으면 `PushPort`로 알림을 보낸다. 알림 문구에는 메시지 내용을 60자까지만 넣는다.
- **[제안]** 서버를 여러 대로 늘릴 때를 대비해 게이트웨이의 전달은 Redis를 거친다(3번에서 도입한 Redis).

### 권한

- 대화, 조건 버전, 계약은 그 협업의 당사자만 읽는다. 남의 것을 ID로 요청하면 404.
- 차단된 대화방에 보내면 409.

## 5. 법적 확인이 필요한 것

- **전자 계약의 효력.** 확인란 동의와 시각 기록만으로 충분한지, 본인 확인이나 전자서명이 필요한지.
- **계약서의 내용.** 여덟 항목 외에 들어가야 할 조항(해지, 손해배상, 분쟁 해결).
- **대화 내용의 보관 기간과 신고 처리 절차.**

## 6. 소유자 확인이 필요한 것

1. **브랜드의 결제 시점.** 계약 동의 때 제작비를 보관하도록 했다. 게시 후에 결제하는 방식을 원하는지.
2. **브랜드가 먼저 말 걸기.** 만들지 않았다. 필요하면 메시지 요청 경로를 하나 더 연다.
3. **가게 오퍼의 조건 수정.** 대화에서 조건을 바꾸지 못하게 했다.
4. **고칠 수 있는 값의 선택지.** 수정 범위, 활용 권한, 지급 조건의 선택지가 맞는지.
5. **신고를 받는 운영자 연락처.**

## 7. 만드는 사람에게 맡기는 것

- 테이블의 정확한 컬럼, 엔드포인트, 게이트웨이의 이벤트 이름
- 대화 목록, 수정 제안, 신고 화면의 배치
- 메시지 목록의 페이지 나누기 방식
